## Current Code Check

Current `map_progression_lab` structure:

```text
r1_main_1..10 are linearly unlocked.
r1_main_5 requires r1_main_4.
r1_bandit currently requires r1_main_4.
r1_prison currently requires r1_main_5.
clearNode always auto-clears.
autoChallenge repeatedly clears nextAvailableNodes by nodeRank.
nodeRank orders main nodes before branch nodes.
```

This means:

```text
If the plan only changes r1_prison to require r1_main_4,
then after M4 the player can still continue directly into r1_main_5.
Auto-challenge will also prefer r1_main_5 over branches because main nodes rank before branch nodes.
```

## Review Finding

Severity:

```text
serious
```

Reason:

```text
The previous implementation plan protects Prison-vs-Camp ordering,
but it does not protect Prison-vs-mainline ordering.
```

Under the player's cognition model, the known behavior is "challenge next level." If M5 is available after M4, the no-cost default behavior is likely to continue mainline. That skips the intended first Prison attempt, so no Prison failure memory is created. Without the failure memory, Camp A is not learned as a key; it becomes just another side reward.

This is the same class of problem as Camp-first:

```text
Key is valid statically,
but the player does not experience the lock before consuming or bypassing the key.
```

## Auto-Challenge Requirement

Current auto-challenge is dangerous because it clears available nodes by rank. In the corrected implementation:

```text
If auto-challenge hits r1_prison first-fail:
  - mark failure
  - stop auto-challenge immediately
  - select/focus r1_bandit
```

Reason:

```text
Auto-challenge should not compress failure -> key -> retry into one unreadable burst.
The player must have a visible failure memory moment.
```

After r1_bandit is cleared, auto-challenge can continue normally.
