# Real Combat Cognition Loop

- Date: 2026-07-10
- Scope: map progression lab, player cognition simulation
- Status: implemented as a first pass

## Why This Pass Exists

Two previous assumptions were wrong:

1. The world-map progression lab used fake clears. That made it impossible to use real combat numbers to block the player, so tuning the map created fake cognition.
2. The simulated player was too mechanical. A real player reacts to failure using what they already know: farm/equip first, then after repeated failure consider team or role changes if the game has taught them those concepts.

The first issue is fixed in the map lab implementation. The second issue is now recorded in `game-analysis-iteration/references/lock-key-cognition.md`.

## Player Cognition Rule

The simulated player is smart but knowledge-bounded:

```text
observe goal and choices
choose the lowest-cost known behavior
run real combat
if success, update knowledge from the visible result
if failure, record attribution using only known concepts
try a different known behavior only after the first explanation axis has visibly failed
```

Early loop:

```text
fail prison -> known explanation is equipment/power -> farm/equip camp
fail after gear attempts -> equipment was tried -> role/team explanation becomes plausible
```

## Real Combat Integration

`map_progression_lab/map-progression-lab.js` now calls `GAME_COMBAT_SIM.simulateTeams` for map-node challenges.

Clear rule:

```text
node challenge -> real combat
left wins -> node clears -> loot rolls -> best gear auto-equips
left loses -> node does not clear -> failure memory/log selects next plausible behavior
```

This is still a lightweight map-lab layer, not the final town progression system. The goal is to make cognitive locks truthful enough that a player can actually fail and recover.

## Map Layout Design

The existing three-region map remains:

- Region 1: gray belt outskirts
- Region 2: old mine hill
- Region 3: black pine border

Each region contains:

- main line: 10 process nodes
- camp / bandit branch: equipment key
- prison branch: character / role reward
- boss: region close
- later regions also include gate nodes

## Enemy Structure

Enemy groups are generated by node type:

```text
early main:
  warrior, warrior, ranger

mid main:
  warrior, warrior, ranger, priest

late main:
  knight, warrior, ranger, mage

gate:
  warrior, warrior, ranger, priest

camp / bandit:
  knight, warrior, ranger, mage

prison:
  warrior, knight, ranger, ranger

boss:
  knight, warrior, mage, priest
```

Enemy scale increases by region, main-node index, and node type:

```text
region base:
  r1 = 0.62
  r2 = 1.25
  r3 = 2.05

node additions:
  main number adds gradual scaling
  branch adds a medium bump
  prison adds extra pressure
  boss adds the largest bump
```

## Field Effects

Map nodes can attach existing runtime field effects:

```text
prison -> sentry_suppression
camp / bandit -> heavy_shield_line
boss -> pressure_corridor
```

This keeps field effects focused on high-cognition moments instead of every filler fight.

## Equipment Handling

This pass uses a minimal map-lab equipment model:

- slots: weapon, armor, focus, boots
- each drop has rarity, level, slot, and power
- highest-power item per slot auto-equips
- equipped gear scales the player's real-combat team

This is intentionally simple. It exists only so the map lab can truthfully test:

```text
failure -> loot/farm -> equip -> retry
```

## Known Limits

- The map lab still has a small automatic equipment model, not the full town equipment UI.
- Text still contains legacy mojibake in some UI sections; this pass avoids broad text rewrite.
- The real combat is deterministic for node/attempt/gear seed, but not yet calibrated by large batches.
- Player behavior is represented in logs and focus selection, not yet as a separate visible agent panel.
