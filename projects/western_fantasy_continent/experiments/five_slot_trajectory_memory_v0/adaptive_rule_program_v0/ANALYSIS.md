# 实验结论：参数化小程序可以覆盖基础变化，也能逐条吸收例外

本实验回答两个问题：基础“同列飞船下降N格”能否在没有写死列、数值和对象数量的情况下复用；新规则不断出现时，能否只修订小程序而不破坏旧行为。

## 基础覆盖

V1程序只有五件事：检查放骰事件、绑定N、遍历当前飞船、选择同列对象、把`row`改为`row+N`。150个生成案例随机改变列、骰子点数、飞船数量、飞船高度和零命中情况，150/150通过。

这证明程序复用来自“角色与变量绑定”，不是记住具体对象或测试答案。

## 增量修订

| 版本 | 新规则 | 旧版在专门新例上的结果 | 修订后 | 修订后累计旧例回归 | 程序大小 |
|---|---|---:|---:|---:|---:|
| V1 | 基础同列下降 | — | 150/150 | 150/150 | 746 bytes |
| V2 | 防空房距离减一 | 0/100 | 100/100 | 250/250 | 1,151 bytes |
| V3 | 冻结飞船不动 | 0/100 | 100/100 | 350/350 | 1,455 bytes |
| V4 | 重型飞船距离减半 | 0/100 | 100/100 | 450/450 | 1,836 bytes |
| V5 | 加速在修正后加一 | 0/100 | 100/100 | 550/550 | 2,219 bytes |
| V6 | 聚焦房只移动最靠近城市的并列目标 | 0/100 | 100/100 | 650/650 | 2,624 bytes |

每个新例组都故意保证新规则一定被触发，所以修订前0%不是自然分布准确率，而是证明旧程序确实没有偷偷覆盖新规则。

V2到V5属于局部参数或逐对象条件。V6需要先看完整候选组，再取`row`最大值并保留并列项；原语言没有这个能力。实验明确增加了一个通用`targetReducer`阶段后才修好，说明遇到结构性新规则时，除了修程序，有时还要扩充程序语言。

## 组合验证

最终版本在300个随机组合案例和100个聚焦整组比较案例中400/400通过。组合覆盖防空、冻结、重型、加速及其叠加顺序；聚焦案例还包含位置更靠前但应先被排除的冻结飞船，以及最前排并列目标。

程序在副本上试运行，输入不被修改。试运行自动记录读取路径：基础案例平均8.25个读取项，最终复杂组合平均18.34个。复杂规则需要更多观察与比较，因此自然产生更多可供连续设想控制器扣费的注意点。

## 可以相信与不能相信的部分

可以相信：

- 参数化程序能复用不同对象、数量、位置和数值。
- 来源约束的小补丁可以增量组合，并通过完整回归避免遗忘旧规则。
- 局部规则不足时，可以明确发现语言缺口，再增加通用计算阶段。
- 封闭试运行可以同时得到候选结果和真实数据依赖轨迹。

尚不能相信：

- 这些补丁由当前同一个AI在看过规则后编写，不是陌生Agent盲生成。
- 测试规则和独立oracle都由本实验设计；这验证结构一致性，不是现实游戏规则理解准确率。
- 冻结、重型、加速、聚焦是压力测试规则，不是官方UFS规则声明。
- 程序继续增长可能变得臃肿；何时分裂成多条程序、如何解决规则冲突尚未测试。

下一步最有价值的验证不是继续加规则，而是把基础程序、受限补丁合同和冻结规则交给一个隔离Agent；它只能看到每轮失败反馈，不能看oracle或评测案例，观察它是否能自主产生相同类型的修订。
